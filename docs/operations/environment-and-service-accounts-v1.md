## 1. Назначение и границы

Этот документ инвентаризирует текущие системные переменные из `server/_core/env.ts` и задаёт целевой контракт окружения для одноразовых ссылок входа, почтового адаптера, серверной проверки промо, платёжного адаптера, объектного хранилища, обработчиков исходящей очереди и загрузчика конфигурационного релиза. Его задача — исключить общие избыточные секреты и смешение полномочий между веб-процессом, фоновыми обработчиками и миграциями.

| Маркер | Значение |
|---|---|
| **Нормативное требование (ТЗ)** | Обязательное требование ТЗ v3. Упоминание требования не означает, что оно уже реализовано. |
| **Проектное решение R0** | Целевой технический контракт. Он не изменяет работающий код и требует отдельного согласования и реализации. |
| **Открытый вопрос** | Решение не принято. Связанный контур нельзя считать готовым или включённым. |

**Проектное решение R0.** Настоящий файл — единственное изменение в рамках этой задачи. Он не изменяет runtime-маршруты, React, схему БД, генерацию PDF, действующую бизнес-логику, фактические значения переменных и права развёрнутых сервисов. Он не закрывает и не меняет текущий клиентский доступ. По аудиту текущие публичные маршруты, где токен играет роль bearer credential, требуют отдельного исправления в Release 1.[2]

**Нормативное требование (ТЗ).** Доступ к диагностике, ответам, документам, отчёту и PDF определяется клиентской серверной сессией и проверкой принадлежности `customerAccountId`, а не знанием токена. Для одноразовой ссылки в БД хранится только хэш; требуются короткий TTL, одноразовое потребление, ограничение частоты запросов и cookie с `HttpOnly`, `Secure`, `SameSite=Lax`.[1]

**Нормативное требование (ТЗ).** В Release 1 реальная оплата не подключается. Промокод проверяется только на сервере; Release 1 включает почтовый адаптер и тестовый транспорт. Промышленная доставка email и платёжный провайдер относятся к Release 3, а документарный тариф — к Release 2.[3]

Под **секретом** в этом документе понимается значение, раскрытие которого позволяет аутентифицироваться, подписывать запросы, читать или менять защищённые данные либо обходить контроль доступа. URL, идентификатор, имя корзины и публичный ключ обычно не являются секретами, но могут быть конфиденциальными служебными настройками и не должны публиковаться без необходимости.

## 4. Целевой контракт переменных окружения

Обозначения: **обяз.** — нужна для включённого контура; **условно** — зависит от согласованного адаптера; **—** — не нужна. «Тест» означает тестовый транспорт или тестовую среду, а не промышленную доставку.

### 4.1. Magic link и клиентская сессия

**Нормативное требование (ТЗ).** В базе хранится только хэш токена одноразовой ссылки. Токен имеет короткий TTL и одноразовое потребление; клиентская сессия отделена от административной авторизации.[1]

**Проектное решение R0.** Raw token существует только в памяти компонента выпуска/отправки. Он не попадает в БД, полезную нагрузку outbox, логи, трассировки, аналитику, URL после consume или клиентское хранилище. Повтор отправки выпускает новый токен в пределах rate limit, а не восстанавливает старый.

### 4.4. Хранилище и обработка документов

**Нормативное требование (ТЗ).** В R1 PDF является рендером общего snapshot. R2 требует приватное объектное хранилище, короткоживущие подписанные ссылки, проверку MIME, размера и контрольной суммы. До анализа документов должны быть определены внешний провайдер, минимизация данных и защита от prompt injection.[1] [3]

**Проектное решение R0.** Отчёты и исходные документы разделяются по разным корзинам либо префиксам. Предпочтительна workload identity; статические ключи допустимы лишь как временный адаптер. Object key не является полномочием чтения, а веб-процесс не получает постоянный глобальный доступ на чтение или перечисление объектов.

### 4.5. Обработчики, outbox и конфигурационный релиз

**Нормативное требование (ТЗ).** Email delivery имеет конечные состояния и ограниченные повторы; статусы и переходы фиксируются до миграций. Юридическое ядро версионируется, а применённые версии должны восстанавливаться по отчёту.[1]

**Проектное решение R0.** Доменный переход записывает outbox-событие в той же транзакции. Отдельный worker получает задачу по lease, использует idempotency key и ограниченное число повторов. Допускается table outbox либо согласованный долговечный брокер; оба варианта требуют отдельной identity, мониторинга и конечного состояния.

## 5. Сервисные аккаунты: минимальные привилегии

**Проектное решение R0.** Каждая роль получает отдельную workload identity, отдельного пользователя БД и отдельный набор окружения для каждой среды. Общий исполняемый образ с несколькими entrypoint не обосновывает общий service account. Все роли ведут структурированные логи без секретов, используют идентификатор запроса/задачи и формируют предусмотренные audit events.

| Роль | Минимально разрешено | Явно запрещено | Разрешённые секреты и настройки | Граница данных и хранилища |
|---|---|---|---|---|
| **web** | Проверять клиентскую/административную сессию и owner/role policy; выполнять owner-bound команды; проверять промо; создавать outbox/audit events; выдавать download grant после owner/status check; проверять подписанный webhook, когда контур включён | DDL; глобальное чтение/перечисление корзин; отправка email; обработка документов; подпись конфигурации; обход access grant; raw token как право | Собственный URI БД; peppers сессии и magic link; verifier промо; readonly config; webhook verifier только при включённом endpoint | Только записи клиента в пределах владельца; хранилище — лишь узкий grant, не прямое чтение корзин. |
| **mail worker** | Claim только email jobs; выпускать/хэшировать magic token при выбранной модели; отправлять письмо; записывать delivery/retry/suppression | Читать answers/reports/documents/payments без необходимости; менять risk/recommendation/access grant; миграции; admin API | Собственный URI БД; `LEXY_EMAIL_*`; magic pepper, если worker выпускает ссылку; readonly base URL и TTL | `outbox`, email delivery, token hash и минимум данных получателя; доступа к хранилищу нет; URL/токен не журналируются. |
| **document worker** | С R2 claim document jobs; читать объект назначенной задачи; scan/extract/classify; записывать metadata/status; создавать escalation/outbox event | Bucket list; выдача download grant; изменение severity/recommendation/legal basis; PDF/email; миграции | Собственный URI БД; секреты проверки; readonly config; identity только documents/quarantine | Только назначенный документ, статусы, извлечение и промежуточные доказательные данные; доступа к reports bucket нет. |

| **migration runner** | Однократно выполнять утверждённые DDL/DML/backfill; записывать migration evidence/reconciliation | HTTP; постоянный worker; email/document/PDF; доступ к runtime secrets других ролей; подпись конфигурации | Временный отдельный URI БД миграций; readonly checksum артефакта миграции | Только целевая БД в утверждённое окно; доступа к хранилищу нет, кроме отдельно согласованного обезличенного evidence. |

Ограничения TypeScript не заменяют привилегии БД.

## 6. Запрещённые практики

| Запрет | Почему | Допустимая альтернатива |
|---|---|---|
| Хранить секрет, raw magic token, промокод или signed URL в git, fixture, golden report, `.env.example`, логе, трассировке или задаче | Неконтролируемое копирование credential и данных | Только имя переменной, маскированный признак наличия либо требуемый криптографический хэш. |
| Хранить секрет в `VITE_*`, клиентском пакете, React state, `localStorage`, URL, query string или fragment | Браузер, history, referrer и расширения раскрывают его | Только server-side secret; клиент получает узкий краткоживущий результат после авторизации. |
| Считать session token, object key, report/document ID либо UUID полномочием | Идентификатор может утечь и не заменяет проверку владельца/роли/статуса | Server session + `customerAccountId`/роль + предикат состояния. |
| Выдать один root key БД, storage или platform всем ролям и средам | Один компрометированный процесс раскрывает весь контур | Отдельные identities, пользователи БД, IAM policies и ключи. |
| Переиспользовать `JWT_SECRET`, magic/promo pepper, webhook secret и config key | Компрометация или ротация одной функции затрагивает остальные | Независимые ключи с разными владельцами и scope. |
| Дать web постоянный bucket-wide доступ | Компрометация HTTP-контура раскрывает документы и отчёты | Exact-object access worker и server-issued grant после проверки. |
| Включить промышленный email или оплату в R1 из-за наличия env | Env не доказывает provider contract, state machine и tests | Test transport + server promo в R1; промышленные контуры — R3. |
| Доверять browser redirect, public endpoint или непроверенному webhook как payment success | Возможна несанкционированная выдача доступа | Подпись, provider event ID, дедупликация, проверка суммы/валюты/тарифа, атомарный переход. |
| Выполнять worker job без lease/idempotency или бесконечно retry | Дублируются письма, PDF и переходы | Ограниченные повторы, задержка, terminal state и мониторинг. |
| Подписывать legal config из web, worker или renderer | Компрометация runtime позволяет подменить юридическое ядро | Изолированный signing pipeline; runtime только проверяет public signature. |
| Называть JSON Schema, checksum или git review юридическим approval | Техническая валидность не подтверждает юридическое содержание | `status=draft_pending_legal_approval` до явного решения уполномоченного лица. |
| Считать этот документ исправлением текущего клиентского доступа | Он не меняет публичные маршруты, bearer tokens или storage proxy | Отдельно реализовать и протестировать access control и magic link в R1. |

## 7. Конфигурационный релиз, изменение и наблюдаемость

**Нормативное требование (ТЗ).** Каждый объект юридического ядра должен иметь идентификатор, версию, даты действия, статус и метаданные обновления; по отчёту восстанавливаются применённые версии.[1]

**Проектное решение R0.** Манифест конфигурационного релиза содержит минимум `releaseId`, `version`, `effectiveFrom`, `effectiveTo`, `updatedBy`, `updatedAt`, `sourceCommit`, `status`, перечень артефактов и SHA-256. Loader работает fail-closed при несовпадении манифеста, контрольной суммы, подписи, канала или политики статуса. Метаданные в шапке фиксируют только нынешний draft и не являются датой вступления в силу или разрешением клиентского доступа.

**Проектное решение R0.** Плановая смена env оформляется записью об изменении: имя, среда, роль, владелец, основание, влияние и план отката без значения. Новый секрет создаётся в secret manager, проверяется в test-среде, выдаётся только нужной роли и после наблюдаемого окна заменяет старый. При подозрении на утечку секрет не передаётся в чат или bug report: создаётся incident record, ограничивается потребитель, выпускается замена, старое значение отзывается, анализируются audit/log events.

| Событие | Разрешённые поля лога | Запрещённые поля |
|---|---|---|
| Запрос magic link | Correlation ID, односторонний fingerprint адреса, результат rate limit, ID шаблона/кампании, service role | Raw token, полная ссылка, pepper, открытый email вне строго нужной записи доставки |
| Попытка промо | Correlation ID, campaign ID, внутренний ID аккаунта/диагностики, результат, отпечаток идемпотентности | Промокод, hash, pepper |
| Webhook | Provider event ID, результат проверки, тип события, проверенные сумма/валюта, correlation ID | Заголовок авторизации, секрет подписи, избыточная raw payload |
| Задача документа | Внутренний ID документа/задачи, результат MIME/размера/checksum, результат перехода | Файл, полный extracted text, signed URL, object key |
| Рендер отчёта | Версия отчёта, hash snapshot/артефакта, версия renderer, ID задачи | Полный snapshot, raw answers, storage credentials |
| Миграция | Checksum миграции, identity исполнителя, среда, итоги reconciliation | URI/пароль БД, выгрузки ПДн, секреты |
