# Lexy v3: путь от текущего Pilot до полной реализации

## Главный вывод

По ТЗ v3 проект движется в правильной последовательности, но текущий результат нельзя считать полностью реализованным сервисом. Сейчас завершены технические вертикальные инкременты Release 1 от контроля доступа до PDF. Остался сквозной E2E-инкремент Release 1, затем необходимы документарный тариф Release 2, коммерциализация Release 3 и отдельная финальная юридическая приёмка.

Критических разделов ТЗ, которые нужно было бы добавить в дорожную карту с нуля, не обнаружено. Однако есть несколько требований, которые ещё не закрыты кодом или вынесены за пределы текущего Pilot: утверждение юридического ядра, ручная проверка эталонных отчётов, operational escalation, политика хранения и удаления данных, migration rehearsal, legacy compatibility risk, полный набор полей целевого отчёта, документарный тариф, production email, реальные платежи и нагрузочное/security-тестирование.

## Текущий статус

| Область | Состояние |
|---|---|
| Release 1 access control | Технически реализован |
| Magic link | Тестовый контур реализован |
| Promo access | Реализован только synthetic Pilot, реальных платежей нет |
| Server-authoritative questionnaire | Реализован для Pilot |
| Deterministic rules engine | Реализован без LLM |
| Immutable web report | Реализован |

| Юридическое утверждение контента | Не проводилось по согласованному решению владельца |
| Реальный клиентский запуск | Запрещён release gate |

## Этап 1. Закрыть Release 1 технически

### 1.1. Завершить E2E-путь

Нужно пройти один полный синтетический сценарий без ручного вмешательства:

1. лендинг платной диагностики;
2. запрос magic link;
3. получение ссылки через тестовый transport;
4. одноразовый вход и создание customer session;
5. принятие обязательных условий;
6. выбор тарифа;
7. серверная проверка промокода `123`;
8. создание `payment_record` со статусом `promo_granted` и нулевой оплатой;
9. создание owner-bound case;
10. прохождение анкеты на desktop и mobile;
11. восстановление прогресса на другом устройстве;
12. отправка анкеты и детерминированный расчёт;
13. построение web snapshot;
14. создание и скачивание PDF;
15. повторная отправка и проверка, что второй report snapshot и второй PDF не создаются.

Отдельно нужна полная негативная матрица: anonymous, владелец, другой клиент, администратор без нужной роли, сервисный worker, старый `sessionToken`, изменённый `publicId`, отозванный grant и неготовый отчёт.

### 1.2. Запустить DB integration suite на чистой disposable-базе

Текущая shell-сессия не имела обязательных harness-переменных для MariaDB. Перед закрытием R1 нужно применить все add-only migrations на пустой disposable-базе, выполнить integration tests и отдельно проверить миграцию `0011_r1_pdf_artifact_expand.sql`.

Нужно также провести migration rehearsal: backup/restore, inventory старых данных, проверку orphan/duplicate/null-состояний и подтверждение, что старые записи не получили владельца через email, cookie, IP или legacy token.

### 1.3. Закрыть Release 0 governance-артефакты

Технические файлы уже существуют, но до полного принятия нужно формально утвердить:

- `questionnaire_v2`;
- `risk_catalog_v1`;
- `rules_v1`;
- `legal_basis_catalog_v1`;
- `recommendation_mapping_v1`;
- `report_schema_v1`;
- state machines для case, payment/access, document, report и email delivery;
- матрицу доступа;
- миграционный план v1 → v2;
- тарифную и credit-конфигурацию;
- 12–15 fixtures с ожидаемыми и запрещёнными результатами.

По ТЗ три эталонных отчёта должны быть проверены и утверждены юристом. Ранее было принято решение отложить юриста до завершения технических этапов. Это допустимо как процессное решение, но означает, что Release 0 и запуск всё ещё формально не приняты.

## Этап 2. Провести финальную юридическую проверку Release 1

После E2E нужно организовать отдельный review не кода, а содержания:

- вопросы и варианты ответов;
- активные риски и критические триггеры;
- уровни риска и override-правила;
- юридические основания;
- допустимые формулировки;
- последствия и финансовые ориентиры;
- дорожную карту 0/30/60/90;
- единственную рекомендацию следующего продукта;
- тексты ограничений и эскалации.

Юрист должен проверить три эталонных сценария и подтвердить, что отчёт не утверждает нарушение без достаточных доказательств, не обещает результат и корректно переводит критические случаи к специалисту.

Важно: прохождение тестов не является юридическим утверждением. Статусы legal artifacts должны изменяться только владельцем процесса после human review.

## Этап 3. Довести operational escalation до реального процесса

Сейчас система умеет обозначить необходимость экспертной проверки. Для полноценного сервиса этого недостаточно. Нужно зафиксировать:

- кто получает заявку;
- через какой канал;
- SLA, например следующий рабочий день;
- какие данные видит эксперт;
- какой статус видит клиент;
- кто отвечает за следующий шаг;
- как фиксируются комментарии и результат проверки;
- что получает клиент сразу: краткое безопасное резюме, экспертный разбор или индивидуальное предложение;
- как отслеживаются просроченные заявки.

До появления ответственного и SLA CTA «Запросить экспертный разбор» остаётся интерфейсным обещанием, а не завершённым бизнес-процессом.

## Этап 4. Release 2 — документарный тариф

Документарный тариф должен быть отдельным расширением, а не просто включением upload-кнопки.

Нужно реализовать:

1. доступ к загрузке только для тарифа `with_documents`;
2. ограничения количества, размера и форматов файлов;
3. проверку MIME, расширения, размера и контрольной суммы;
4. приватное объектное хранилище и короткоживущие owner-bound ссылки;
5. четыре поддерживаемые категории документов;
6. состояния документа: uploaded, extracting, analyzed, manual_review_required, failed, deleted;
7. text extraction для PDF/DOCX;
8. requestedDocumentCategories и подсказки приоритетных файлов;
9. связь документа с конкретным риск-блоком и evidence fragment;
10. статус «подтверждено предоставленным документом» только после выполнения всех условий из §14.4;
11. запрет prompt injection: документ является недоверенными данными, а не инструкцией;
12. запрет модели менять риск, доказательность и рекомендацию;
13. ручную эскалацию для нечитаемых, противоречивых или защищённых файлов;
14. повторную генерацию новой версии отчёта без перезаписи предыдущей;
15. удаление документа с сохранением неизменности ранее выданного отчёта.

Документарный тариф нельзя объявлять готовым, пока не определены provider, модель, DPA, место обработки, сроки удаления и запрет обучения на клиентских данных.

## Этап 5. Release 3 — коммерциализация

После технической и юридической проверки Pilot можно подключать коммерческий контур:

- production email provider, подтверждённый домен и доставка magic link;
- production-письма о готовности отчёта;
- реальный платёжный provider;
- webhook, idempotency, provider payment ID, возвраты и reconciliation;
- автоматический зачёт 6 900 ₽ в течение 14 дней;
- импорт бесплатной диагностики в клиентский профиль только по безопасному механизму связывания;
- полная история операций;
- расширение анкеты до полного ядра 45 вопросов и до 15 веточных вопросов;
- расширение risk catalog на отрасли и новые сценарии;
- включение LLM только как контролируемого редактора после достаточного числа проверенных кейсов;
- аналитика полной воронки;
- CRM-очередь экспертных обращений;
- нагрузочное и security-тестирование.

LLM на этом этапе по-прежнему не должна менять уровень риска, критический override, доказательность или рекомендацию. Она может только перефразировать разрешённые блоки и собирать summary по валидированной структуре.

## Этап 6. Политика данных и эксплуатационная готовность

До открытия доступа реальным клиентам нужно отдельно утвердить и реализовать:

- срок хранения неактивного черновика;
- срок хранения завершённой анкеты;
- срок хранения исходных документов;
- срок хранения PDF;
- срок хранения magic tokens и email delivery logs;
- удаление аккаунта и его последствия;
- удаление документа до генерации отчёта;
- восстановление файлов;
- retention audit log;
- резервные копии отдельно от рабочей базы;
- запросы на удаление с защитой обязательных финансовых и операционных записей;
- права администратора и журналирование всех административных действий;
- ротацию секретов и процедуру отзыва сессий;
- мониторинг ошибок, очередей, PDF, email и storage;
- alerting и rollback plan.

## Этап 7. Legacy, безопасность и запуск

До полного запуска необходимо решить, что делать с legacy-контуром. Сейчас старые token routes и старые платные/free procedures сохраняются как compatibility risk. Это означает, что нельзя заявлять глобальное соответствие требованию owner-bound доступа, пока не выполнено одно из решений:

1. legacy маршруты полностью закрыты или переведены на безопасную совместимость;
2. legacy данные явно изолированы и обозначены как отдельный неподдерживаемый contour;
3. выполнена контролируемая миграция с подтверждённым ownership, без вывода владельца из email или токена.

После этого нужны security-проверки:

- BOLA/IDOR для всех locator-ов;
- session fixation, replay и race для magic link;
- CSRF и cookie policy;
- rate limits;
- SSRF и path traversal для документов и storage;
- prompt injection для документов;
- утечки через access logs, Referer, analytics и error tracking;
- права object storage;
- админские роли и audit log;
- dependency и secret scanning;
- нагрузочное тестирование полного пути.

## Финальный launch gate

Реальный доступ клиентам можно открывать только после одновременного выполнения следующих условий:

- три эталонных отчёта утверждены юристом;
- legal basis и допустимые формулировки утверждены;
- Release 1 E2E и DB rehearsal пройдены;
- production magic link работает с подтверждённым доменом;
- политика хранения и удаления опубликована и технически исполняется;
- expert queue имеет ответственного и SLA;
- legacy compatibility risk закрыт или изолирован;
- security и load tests пройдены;
- backup/restore проверены;
- нет обхода доступа через старые public routes;
- включённый runtime bundle имеет approved status;
- client runtime flag переведён из fail-closed только после финального review.

До этого статус проекта должен оставаться: **R1 technical build/test; client launch prohibited**.

## Что сейчас действительно не упущено

В текущем плане присутствуют все крупные продуктовые части ТЗ: анкета, deterministic rules engine, web report, PDF, доступ, magic link, promo, документарный тариф, платежная модель, credit entitlement, LLM-ограничения и E2E. Основные риски не в отсутствии раздела, а в том, что несколько разделов ещё являются техническими заготовками или будущими релизами.

Самые важные недостающие элементы на текущем этапе — это E2E и MariaDB rehearsal, юридическое утверждение трёх эталонных отчётов, operational escalation, formal data-retention policy и закрытие legacy routes. Их нужно считать отдельными workstreams, а не мелкими задачами внутри UI.
